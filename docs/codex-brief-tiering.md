Donc claude-opus-4.8 (105) = frontier mais claude-opus-5.5 (82, plus récent, plus fort, moins cher) = premium; une tâche critique choisit Opus 4.8. Avant correctif: voir /workspace/before.txt (copie-le dans la preuve).
À faire (conçois la meilleure approche simple, réutilise l'existant, pas de refonte):
1. Découpler tier et prix: retirer la règle cost_index→frontier. Le tier vient d'un score de capacité.
2. Score de capacité à partir des données GitHub déjà synchronisées: github_category (Lightweight/Versatile/Powerful), model-comparison.yml (task_area, excels_at: ex. "deep reasoning", "long-horizon", "complex" → bonus; "fast", "simple" → malus), fenêtre/tiers de contexte si dispo, statut, et génération dans une lignée (parse famille+lignée+version: Claude Opus 4.8 < 5 < 5.5; GPT-6 Sol > GPT-5.6 Sol; variantes "fast" = même capacité). Mappe score→tier. Contrainte dure de monotonie: dans une lignée, une version plus récente n'a jamais un tier inférieur à une plus ancienne (applique un passage de monotonie après le scoring). Documente hypothèses et poids; dis clairement que ce sont des métadonnées GitHub, pas des benchmarks. Permets un override manuel `tier_override` dans models.yaml (prioritaire, documenté) mais n'en dépends pas pour corriger Opus 5.5.
3. Nouveaux modèles (sync_registry): tier calculé par le même score, jamais par le prix. Signaux insuffisants (pas de comparatif, lignée inconnue) → `tier_provisoire: true`, tier prudent (catégorie seule), avertissement; ne jamais rétrograder parce qu'il est moins cher.
4. Prix = budget (--max-cost, code 2) + départage à tier égal seulement. Vérifie que « meilleur tier ≤ demandé puis moins cher » tient. Régénère models.yaml/models.json via la nouvelle logique (sync en local --upstream-dir upstream ou réseau), en préservant les champs manuels.
5. Classification « critique » dans route.py: un seul mot (paiement, auth, migration...) ne suffit plus. "faille", "CVE", "vulnérabilité", "injection", "fuite de données", "production", "perte de données", "rollback", type bug sur domaine sensible...).
